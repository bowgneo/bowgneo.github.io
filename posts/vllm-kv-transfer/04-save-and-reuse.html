vLLM 请求调度（四）：AscendStore 的 KV 保存与复用

章节导航
  1. get_num_new_matched_tokens：Scheduler 查询前缀
  2. start_load_kv：Worker 加载命中的 KV
  3. wait_for_save：Worker 保存 KV

这一节讨论 AscendStore 池化的非逐层模式（use_layerwise=False）。假设共享池里已有一段前缀 KV。Scheduler 先查能复用多少，Worker 再把命中的 KV 读入 NPU，执行 forward 后保存本轮可复用的 KV。下面以同步加载（load_async=False）为例。

get_num_new_matched_tokens：Scheduler 查询前缀

Scheduler 先通过 KVCacheManager 查本地前缀，再把本地命中的 token 数传给调度侧 Connector。AscendStore 用请求的 block_hashes 查询共享池，返回本地命中之外还可以加载多少 token。 Scheduler._get_local_prefix_cache_hit(request) · KVPoolScheduler.get_num_new_matched_tokens(request, num_computed_tokens)

池里命中的 KV 需要有地方写入。Scheduler 通过 allocate_slots() 分配本地 blocks，成功后才调用 update_state_after_alloc()，把这些 blocks 告诉 Connector。调度侧 Connector 最后用 build_connector_meta() 汇总本轮的加载和保存信息。 Scheduler.schedule(throttle_prefills) · KVPoolScheduler.build_connector_meta(scheduler_output)

start_load_kv：Worker 加载命中的 KV

多进程执行时，EngineCore 把 SchedulerOutput 交给 MultiprocExecutor。Executor 通过 RPC 把计划发给 NPUWorker，Worker 再调用本进程里的 Model Runner V2。EngineCore.step() · NPUWorker.execute_model(scheduler_output)

前面生成的 metadata 就在 SchedulerOutput.kv_connector_metadata 里。其中的 connector_metadata.requests 是请求元数据列表，每条 ReqMeta 带着请求 ID、本地 block IDs 和加载、保存信息。 ReqMeta

class ReqMeta:
    req_id: str
    save_end_token: int
    # ...
    block_ids_by_group: list[list[int]]
    # ...
    save_start_token: int = 0
    can_save: bool | None = None
    load_spec: LoadSpec | None = None

ActiveKVConnector.pre_forward() 先绑定 metadata。因为这轮有同步加载（has_sync_kv_loads=True），它在 forward 前调用 Worker 侧 Connector 的 start_load_kv()。后端用 GET 把 KV 写进 Scheduler 分配好的本地 blocks。加载成功后，forward 可以直接读取这段前缀。 ActiveKVConnector.pre_forward(scheduler_output, **kwargs) · KVPoolWorker.start_load_kv(metadata)

wait_for_save：Worker 保存 KV

本轮新算出的 KV 也可以存回共享池。Model Runner V2 在采样收尾时调用 ActiveKVConnector.post_forward()，Worker 侧的 wait_for_save() 在这里提交保存任务。 ActiveKVConnector.post_forward(finished_req_ids, wait_for_save=True) · AscendStoreConnector.wait_for_save()

发送线程拿到任务时，NPU 可能还在写这一轮的 KV。模型线程在计算流上记录一个 event，流执行完这些写入才会到达它。同一轮的保存任务共用这个 event。 KVPoolWorker.wait_for_save(connector_metadata)

current_event = None
# ...
send_thread = self.kv_send_thread
requests: list[ReqMeta] = []

for request in connector_metadata.requests:
    can_save = request.can_save
    if can_save is None or not can_save:
        continue
    if current_event is None:
        current_event = torch.npu.Event()
        current_event.record()
    # ...
    request.current_event = current_event
    requests.append(request)

# ...
if requests:
    self._previous_save_batch = send_thread.add_save_batch(requests)
send_thread.request_queue.join()

发送线程等 NPU 执行到这个 event，再从设备 blocks 读出 KV，写入共享存储。 KVCacheStoreSendingThread._handle_stored_request(req_meta)

if current_event is not None:
    current_event.synchronize()
if self.m_store.put(keys, addrs, sizes) is False:
    return

一项保存任务处理完，发送线程就在 _handle_request() 的 finally 中调用 task_done()。队列里的任务全部处理完后，模型线程的 request_queue.join() 才返回。 KVCacheStoreSendingThread._handle_request(req_meta)

为什么要调用 request_queue.join()

PUT 直接从设备 blocks 读取 KV。假如本轮要保存 block 12，后续 forward 却先把新 KV 写进同一个 block，发送线程就可能把新 KV 存到旧前缀的 key 下。这就是模型线程要等保存队列处理完的原因。
